# Ecological Dataset Freshness Monitor

A lightweight monitor for key ecological data APIs. It runs on a schedule (via
GitHub Actions cron) and checks each dataset for three failure modes:

- **🔴 Broken API** — the request errors, times out, or returns a non-2xx status
- **🔴 Schema change** — the response's field structure no longer matches the
  last known-good baseline (a strong signal the provider changed their API)
- **🔴 Stale data** — the most recent record is older than an acceptable
  threshold for that dataset

When any issue is detected, it sends an alert to a configured webhook
(Slack/Discord-compatible) and fails the CI job so it's visible in the repo's
Actions tab.

## Monitored Datasets

| Dataset | What it is |
|---|---|
| **USGS NWIS** | National Water Information System — real-time streamflow/water data |
| **GBIF** | Global Biodiversity Information Facility — species occurrence records |
| **EPA Water Quality Portal (WQP)** | Joint USGS/EPA water quality station data |
| **ESA WorldCover** | Global 10m land-cover classification (via Planetary Computer STAC) |
| **Global Forest Watch** | Forest change/deforestation monitoring (WRI) |

Exact endpoints, freshness thresholds, and field paths are defined in
[`config.yaml`](./config.yaml) — that's the file to edit if a provider changes
their API shape and a mapping needs updating.

## How It Works

1. `monitor.py` reads `config.yaml` and hits each dataset's API
2. For JSON APIs, it fingerprints the top-level field structure and compares
   it against `state/schema_baseline.json` (auto-created on first run)
3. Where a freshness timestamp field is configured, it checks the most recent
   record's age against that dataset's `max_staleness_days`
4. Results are written to `state/status.json`
5. If anything's wrong, an alert is POSTed to the webhook URL in the
   `WEBHOOK_URL` environment variable / repo secret
6. `dashboard/render_status.py` regenerates the table below from
   `state/status.json`

## Setup

```bash
pip install -r requirements.txt

# first run — creates the initial schema baseline
python monitor.py --update-baseline

# subsequent runs — will flag drift from that baseline
python monitor.py
```

### Automated runs (GitHub Actions)

This repo includes [`.github/workflows/monitor.yml`](./.github/workflows/monitor.yml),
which runs the monitor every 6 hours, regenerates this README's status table,
and commits the result back to the repo automatically.

To enable alerts, add a repository secret named `WEBHOOK_URL` pointing to a
Slack or Discord incoming webhook (Settings → Secrets and variables → Actions).
Without it, the monitor still runs and updates `status.json`/this README — it
just won't push a chat notification.

### Manual dataset check

```bash
python monitor.py --dataset "GBIF"
```

### Accepting a legitimate schema change

If a provider deliberately changes their API and the new shape is correct
(not an error page), re-baseline it:

```bash
python monitor.py --update-baseline
```

## Known Limitations

- Field paths in `config.yaml` are best-effort based on each provider's public
  docs at the time this was built. A provider changing their JSON shape is
  exactly the kind of thing this tool is meant to catch — if a `schema_change`
  fires immediately after setup rather than after a real change, check
  `state/status.json`'s `detail` field before assuming it's a false positive.
- EPA WQP, GBIF, ESA WorldCover, and Global Forest Watch don't expose a
  reliable, single "last updated" timestamp in the endpoints used here (GBIF's
  default query has no explicit sort, so the first result isn't guaranteed to
  be the most recent; WorldCover has no fixed release cadence) — those four
  are checked for `broken_api` and `schema_change` only, not staleness. Only
  USGS NWIS currently has staleness checking enabled.
- This is a single-process script intended for scheduled batch runs (cron/
  GitHub Actions), not a continuously-running service.
